# Restore drill (prod Postgres backups)

Companion to `deploy-prod/backup/pg-backup.sh` (`docs/plans/prod-deploy.md` §3 Session 5, §6).
Every backup is `pg_dump --format=custom`, AES-256-CBC/PBKDF2-encrypted client-side, uploaded to
the prod bucket's private `backups/daily/` (and, on Sundays, also `backups/weekly/`) prefix.

**Run the drill below periodically (at minimum: once before go-live, per `docs/plans/
prod-deploy.md` §4 step 20, and again after any change to `pg-backup.sh`'s dump/encrypt format).**
It only ever restores into a **disposable** database — never the real `ammari` database, per
`CLAUDE.md`'s local-safety rule. For an actual production incident, skip to "Real disaster
restore" at the end of this file instead.

**`deploy-prod/restore-drill-local.sh` (Session 8) automates every step below** — run that
instead of typing these commands by hand; this file documents what it actually does under the
hood, and is still the one to follow for the manual steps or if the script itself needs
debugging.

## What you need

- `PG_BACKUP_ENCRYPTION_KEY` — from `~/ammari-secrets/prod-backup.env` (or your password
  manager; it was generated by `deploy-prod/make-prod-env.sh` and is never stored anywhere else).
- The prod S3 credentials (`S3_ENDPOINT`/`S3_REGION`/`S3_BUCKET`/`S3_ACCESS_KEY_ID`/
  `S3_SECRET_ACCESS_KEY`) — from `~/ammari-secrets/prod-admin.env`.
- Docker, on whatever machine you're running the drill from (your Mac is fine — this never
  touches the prod VPS).

## Drill: restore into a disposable local Postgres

All of this runs on your own machine, never against the real `ammari` database or the prod `db`
container.

### 1. Pick the backup to restore

List what's available (replace the four `S3_*` values from `prod-admin.env`):

```bash
docker run --rm \
  -e AWS_ACCESS_KEY_ID="$S3_ACCESS_KEY_ID" \
  -e AWS_SECRET_ACCESS_KEY="$S3_SECRET_ACCESS_KEY" \
  -e AWS_DEFAULT_REGION="$S3_REGION" \
  --entrypoint /bin/bash \
  amazon/aws-cli:2.27.49 \
  -c 'mkdir -p "$HOME/.aws" && printf "[default]\ns3 =\n    addressing_style = path\n" > "$HOME/.aws/config" && aws s3 ls "s3://'"$S3_BUCKET"'/backups/daily/" --endpoint-url "'"$S3_ENDPOINT"'"'
```

Note the newest key, e.g. `backups/daily/2026-10-17_0215.dump.enc`.

### 2. Download + decrypt it

```bash
WORKDIR="$(mktemp -d)"
KEY="backups/daily/2026-10-17_0215.dump.enc"   # from step 1

docker run --rm \
  -e AWS_ACCESS_KEY_ID="$S3_ACCESS_KEY_ID" \
  -e AWS_SECRET_ACCESS_KEY="$S3_SECRET_ACCESS_KEY" \
  -e AWS_DEFAULT_REGION="$S3_REGION" \
  -v "$WORKDIR":/out \
  --entrypoint /bin/bash \
  amazon/aws-cli:2.27.49 \
  -c 'mkdir -p "$HOME/.aws" && printf "[default]\ns3 =\n    addressing_style = path\n" > "$HOME/.aws/config" && aws s3 cp "s3://'"$S3_BUCKET"'/'"$KEY"'" /out/dump.enc --endpoint-url "'"$S3_ENDPOINT"'"'

PG_BACKUP_ENCRYPTION_KEY="$(cat ~/ammari-secrets/prod-backup.env | grep '^PG_BACKUP_ENCRYPTION_KEY=' | cut -d= -f2-)"
openssl enc -d -aes-256-cbc -pbkdf2 -pass env:PG_BACKUP_ENCRYPTION_KEY \
  -in "$WORKDIR/dump.enc" -out "$WORKDIR/dump.custom"
```

(`PG_BACKUP_ENCRYPTION_KEY` is exported into this shell only — it never appears in a command's
argv, same rule `pg-backup.sh` itself follows.)

### 3. Start a disposable Postgres and restore into it

```bash
docker network create ammari-restore-drill 2>/dev/null || true
docker run -d --name ammari-restore-drill-db \
  --network ammari-restore-drill \
  -e POSTGRES_USER=ammari -e POSTGRES_PASSWORD=drill -e POSTGRES_DB=ammari_scratch \
  pgvector/pgvector:pg16

# wait for it to be ready
until docker exec ammari-restore-drill-db pg_isready -U ammari -d ammari_scratch >/dev/null 2>&1; do
  sleep 1
done

docker cp "$WORKDIR/dump.custom" ammari-restore-drill-db:/tmp/dump.custom
docker exec ammari-restore-drill-db pg_restore -U ammari -d ammari_scratch --no-owner --no-acl /tmp/dump.custom
```

### 4. Spot-check row counts

Compare against what prod currently reports for the same tables (via the admin's own DB access,
or `docker compose exec db psql ...` on the VPS — never write to the real `db` from here):

```bash
docker exec ammari-restore-drill-db psql -U ammari -d ammari_scratch -c "
  select 'products' as t, count(*) from products
  union all select 'orders', count(*) from orders
  union all select 'customers', count(*) from customers;
"
```

Numbers should be close to (or exactly match, if no writes happened between the backup and this
check) what prod reports for the same tables right now.

### 5. Clean up

```bash
docker rm -f ammari-restore-drill-db
docker network rm ammari-restore-drill
rm -rf "$WORKDIR"
unset PG_BACKUP_ENCRYPTION_KEY
```

Nothing from this drill is left running or on disk afterward.

## Real disaster restore (manual, owner-run only — NOT part of any automated pipeline)

Use this only for an actual incident (data corruption, a bad manual change, accidental deletion)
— never as part of a normal deploy or rollback. This is a deliberate, manual procedure by design,
same spirit as `CLAUDE.md`'s "never wipe local data without asking" rule applied to prod: nothing
in the deploy pipeline is ever allowed to run this automatically.

1. **Stop the app containers first** (so nothing is writing to `db` during the restore):
   ```bash
   cd /opt/ammari-prod
   docker compose stop admin-blue admin-green web-blue web-green
   ```
2. **Take a fresh backup of the current (possibly-corrupt) state before touching anything**,
   even if it's bad — you may need to compare against it later:
   ```bash
   ./backup/pg-backup.sh
   ```
3. **Download + decrypt the backup you want to restore** — steps 1–2 of the drill above, run
   from the VPS (or your Mac, copying the decrypted `dump.custom` across via `scp` — never leave
   it sitting in `~/ammari-secrets` or any other long-lived path afterward).
4. **Restore into the real `db` container's volume.** This replaces live data — there is no
   undo beyond step 2's fresh backup:
   ```bash
   docker cp dump.custom ammari-prod-db-1:/tmp/dump.custom   # adjust container name per `docker compose ps -q db`
   docker compose exec db pg_restore -U ammari -d ammari --clean --if-exists --no-owner --no-acl /tmp/dump.custom
   ```
5. **Confirm row counts** against what you expect (see the drill's step 4) before restarting
   anything.
6. **Restart only the slots that were actually active** (never blindly start both colors — that
   would bring up a slot Caddy isn't pointed at and that never got stopped cleanly):
   ```bash
   docker compose up -d "admin-$(cat active-slot-admin)" "web-$(cat active-slot-web)"
   ```
7. Tell the payment gateway / any affected customers only if the incident actually affected
   customer-visible data — this is a judgment call, not a scripted step.
